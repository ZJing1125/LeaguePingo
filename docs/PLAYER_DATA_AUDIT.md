# 国服玩家数据核验与完成清单（BUG-0060/0063）

本批落实用户批准的“排位 → 真实分页/单场 → 时间线”核验方法。代码检查和合成测试可在Linux执行；当前开发机没有Windows客户端，也没有腾讯/WeGame账号会话。BUG-0063根据用户的新实机截图确认非本人零负是成组出现的受限字段并修正产品解释；仍不能将Linux测试通过标记为Windows候选已实机恢复。

## Windows执行入口

前提：Windows amd64、已安装仓库锁定的Go工具链，Git Bash，国服客户端已登录且处于空闲首页/组队房间/结算。不要在匹配、选人、载入或游戏过程中执行。诊断不依赖退出当前助手，不修改客户端；它不是产品程序，不生成/登记交付exe。最好等待助手的资料准备完成，避免两者请求竞争影响耗时判断。

```bash
bash scripts/audit-player-data.sh rank
bash scripts/audit-player-data.sh history
bash scripts/audit-player-data.sh match
# 或一次执行以上全部；不再重复分别执行
bash scripts/audit-player-data.sh all
```

默认核验当前账号。其他玩家使用环境变量，不写进脚本/仓库；不要把含真实ID的命令、shell历史或屏幕录制作为证据提交：

```bash
LEAGUEPINGO_AUDIT_TARGET='玩家名称#标签' bash scripts/audit-player-data.sh all
```

入口拒绝非Windows和跨目标覆盖。原有 `TestLiveRankedSourceComparison` 与分页测试保留；普通 `verify.sh` 不开启本诊断。新测试默认跳过，只有上述入口明确启用才访问客户端。

每次总预算45秒，串行、单玩家；排位SGP尝试仍用生产的1.2秒预算。history/all最多3页（60条原始记录），match最多1页；每页4秒，单场详情与时间线各源各最多5秒。不自动重试、不穷尽历史、不跨大区、不访问OP.GG玩家接口、不读取WeGame Cookie。每步前后重新读取当前账号和阶段；换号、断线、进入不允许阶段后中止，后续标记not_run，在途请求仍受各步超时限制。

## 报告与判读

控制台 `PLAYER_DATA_AUDIT` 后为单行JSON。仅保留固定字段的计数、覆盖、耗时和排位数值：无姓名、PUUID、比赛编号、完整URL、授权、原始响应或原始错误，不自动写盘/上传。需要留证时仅保存这条脱敏JSON至本机artifacts，不提交真实数据。

状态 `verified` 仅表示该步请求和结构核验完成；不表示所有字段齐全或与WeGame/界面一致。`partial`为范围/容器不足，`different`为两源差异，`failed`为请求/解析失败，`not_available`为缺少上游比赛/详情，`interrupted/not_run`为中止/未执行。任何非verified使测试非零退出，仍先打印已完成报告；诊断差异不是产品回退策略。某一源不可用不等于另一源也不能支撑功能。

| 步骤 | 观察字段 | 判断方法 |
| --- | --- | --- |
| rank_lcu | queues、queueMap、combined各自的两队列段位/LP/胜负，response_received | 请求有响应但combined少队列，检查双容器缺失/冲突；单独容器之间的0与非0不能靠顺序猜 |
| rank_sgp | 独立授权后的排位/赛季/胜负、elapsedMs、deadline_exceeded | 失败或触及1.2秒截止不能宣称来源无数据；需区分访问/解析与预算问题 |
| rank_compare | 不同字段名、比较队列数、same_known_season | SGP与LCU不同即记录different；season缺失时不能假定同赛季。与WeGame还须人工对齐身份/大区/队列/赛段 |
| season/mastery | 可信当前赛季是否取得、实际熟练度条目数 | 空数组可能是已知无记录；熟练度等级/积分须在产品界面同客户端核对，不换算场次 |
| history_page_N | 原始返回/解析/排除/重复数 | 后页应是不同比赛；原始偏移递增，重复页立即结束；原始ID只在内存比对 |
| sample_analysis | unique_games、420/440各自赛季/12小时/月胜负、已知胜负、位置有效数、时间边界 | 最多60条只能验证已读样本；三个boundary_reached为0时不能把读到的样本称完整时段/赛季。到达边界也须核对相关指标字段是否齐全 |
| detail_lcu/detail_sgp | 同一局两源的players、targets、full_5v5及各字段覆盖数 | 非5v5有自己的真实人数；0值算已提供。某列覆盖不足人数就是字段缺失，不能补0；完整5v5才有团队分母 |
| detail_compare | 同局按参与者编号比较后不同的固定字段名 | 无逐人数据导出；同场不同值/空值差异应追查来源与解析，不能自动选较大值；不比较名称或抓取对手资料 |
| timeline_lcu/timeline_sgp | 帧数、事件类型计数、坐标数、full_team_gold_frames | 出装需要购买等事件，加点需要SKILL_LEVEL_UP，经济曲线需要完整队伍金币帧。事件数0可能本局没有该事件，不能单凭0断言端点不支持 |

完整比赛优先从已读页选择最近的420/440；没有排位时选最近已读比赛。两种详情与时间线各自显式核验，不让自动回退掩盖某条来源失败；不会扫描更多比赛寻找“成功案例”。无已读比赛时详情/时间线标not_available。

## 闭环标准

1. 对原0负场玩家分别运行rank/all，与客户端或WeGame同一统计范围人工对照。记录两源差异与产品最终数值。原始来源正确而界面错误，才定位缓存/绑定；来源就不正确则继续调查授权/大区/统计服务。
2. 已读样本按模式手工点数核对胜负、KDA和英雄；独立统计还须按SCOUTING进行赛季/12小时/30天完整性验收。60条诊断不能冒充后台完整准备结果。
3. 在产品显式读取对应单场，逐人核对结算整数、补刀/分钟、参团/伤害占比，至少单双排/灵活/特殊模式各一场。JSON只证明字段覆盖，数值正确性以对照为准。
4. 显式读取时间线，以同场回放核对真实购买/出售/撤销、加点和关键事件。地图仅采样点，不是连续路径。若没有真实过程数据，不由终局反推。
5. 界面分别切10/50场、翻页、换英雄、单双排/灵活，确认段位聚合及独立Scout统计不被列表筛选改变；账号/比赛切换不串数据。Windows DPI与加载快览另按ACCEPTANCE核验。
