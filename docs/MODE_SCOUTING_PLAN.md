# 多模式玩家统计与侧边栏扩展方案

日期：2026-11-13。状态：**M1–M4代码已实施；竞技场公共契约与合成回归已核验，新增MS1–MS7国服实机待执行**。用户确认现有玩家统计仅支持单双排/灵活，要求扩展。本文是新增需求，不将既有18项用户PASS扩展为本功能通过，也不改变原34项优化任务的统计。

实施记录（BUG-0138）：Go与前端共享scout_modes.json，已接入精确队列聚合、非排位30天英雄表现、队列覆盖/时间、部分刷新合并、单页公平调度及三处界面。先按英雄索引再汇总，避免每个英雄/模式扫描整份历史；无记录的非排位英雄队列不发送空对象，控制十人快照大小。没有增加新取数服务或统计落盘。绑定由固定Wails CLI生成，自动验证与Windows CI以本提交记录为准，新功能尚未获得国服实机反馈。

## 1. 目标与现状依据

进入海克斯、普通大乱斗或其他已支持模式时，侧边栏、局内快览和主程序当前对局的玩家表现默认跟随本局模式；统计范围、段位参考和攻略来源各自明确。选人确认前也能先查看已有玩家资料。

当前限制来自多个位置，不是增加两个切换按钮即可完成：

- `internal/core/scouting.go`：整体与英雄统计均固定遍历420/440。
- `internal/engine/scouting.go`、`scouting_state.go`：选择入口只接受420/440，非排位保留旧选择或默认420。
- `frontend/src/scoutStats.ts`、`PlayerCardData.vue`、`SidebarPlayer.vue`：非440统一解释成单双排；英雄主指标依赖赛季记录。
- `OverlayView.vue`、`MatchRoom.vue`、`ReviewRoom.vue`及进度组件同样使用该选择，必须一起迁移。
- `internal/guides/model.go`已有多模式攻略识别，但不驱动玩家统计。
- `prepareScouting`虽然有两路并发，分配单位仍是一名玩家；`runScoutCursor`内部连续读取该玩家多页。前两人历史较多时，后续玩家可能等待，需在本次设计中纠正。

## 2. 模式与统计口径

采用一个公共模式目录，保存精确queueId、模式名称、地图/模式校验、可用指标、排位队列及攻略映射。LCU房间、选人、gameflow的已有字段继续作为识别来源；不新增模式轮询。历史记录按每场自身的queueId分类，不能把历史套上当前对局的模式。

| 模式 | 精确队列 | 玩家卡默认口径 | 特有显示 |
| --- | --- | --- | --- |
| 单双排 | 420 | 本英雄本赛季；全英雄12小时/30天 | 对应段位、30天真实分路 |
| 灵活 | 440 | 本英雄本赛季；全英雄12小时/30天 | 对应段位、30天真实分路 |
| 海克斯大乱斗 | 2400 | 本英雄近30天；全英雄12小时/30天 | 模式胜率、场次、KDA；不显示峡谷分路 |
| 普通大乱斗 | 450 | 本英雄近30天；全英雄12小时/30天 | 与海克斯独立；不显示峡谷分路 |
| 普通峡谷匹配 | 400/430/490各自独立 | 本英雄近30天；全英雄12小时/30天 | 已知峡谷分路；排位段位仅为参考 |
| 无限火力 | 900/1900各自独立 | 本英雄近30天；全英雄12小时/30天 | 不推断常规分路，不合并随机变体 |
| 极限闪击 | 1300 | 本英雄近30天；全英雄12小时/30天 | 不显示常规分路 |
| 竞技场 | 1700/1710各自独立 | 本英雄近30天；全英雄12小时/30天 | 平均名次、夺冠率；名单/小队完整时显示前半区率，各自独立有效分母 |

相同攻略类别不代表相同玩家统计范围：例如900与1900可共用攻略适配器，历史计数仍分开。未知队列或明确冲突显示“模式待确认”或未支持状态，不自动回落为单双排；后续确认有效模式时更新本局上下文。

非排位推荐用30天作为主要统计窗口，以减少赛前等待并贴合当前表现。原有真实熟练度保留为全部模式经验；“本季全模式场次”降为已有数据的补充信息，注明本季/本季已读，不为这个次级标签额外自动扫描整赛季。本赛季英雄统计在排位中保留。

### 统计定义

- 胜率使用本队列、对应时间窗口内胜负已知且非重开的对局；缺失不计负场。
- KDA保持现有合计口径；平均K/D/A只以三个字段均有效的对局为分母，同时保存有效样本数。
- 分开记录读取记录数、有效对局数、重开数和各指标分母。重开单列，不加入胜率/KDA；需要按模式核对结果规则，不能按时长单独判定重开。
- 全英雄12小时/30天与当前英雄表现分别标注，避免把全模式、全英雄胜率读成当前英雄胜率。
- 样本少照实显示，不等待补足20场。未覆盖完整时间窗时显示“已读N场”；覆盖确认后才可显示该窗口0场。
- 竞技场的`win`不直接解释为夺冠，缺少名次契约时不显示推算的夺冠率，也不使用固定5v5团队分母。

## 3. 交互与信息布局

顶部保留“玩家资料 / 本局攻略”，玩家资料下将双排切换改为紧凑选择器：默认“本局：海克斯大乱斗 · 自动”。参考其他模式时显示“本局：海克斯 / 查看：单双排参考”，提供一键恢复跟随。攻略页不显示玩家统计筛选器；攻略始终跟随真实对局。

自动选择在真实队列变更、新对局或换账号时更新。手动参考只在当前对局内保持；选人→加载→局内的正常阶段转换不应丢失选择，前提是队列和本局身份一致。新局恢复自动。主窗、侧栏、快览共享当前选择；赛后归档保存当局模式和统计快照，归档筛选只作用于归档。

以下为海克斯展开卡的信息顺序示意，非运行截图：

卡片保持现有头像、英雄图、统一字号和主题。收起时显示身份、当前英雄、所选模式下的场次/胜率/KDA；展开再显示两个时间窗口与参考信息。海克斯/普通大乱斗移除位置环，改为两列紧凑指标；排位保留分路分布。无需为不存在的分路添加替代评分或装饰圆环。

非排位不生成“海克斯段位”“尚未定级”等误导信息，已有单双排/灵活段位放在明确标注的排位参考行。常见320侧栏、280窄侧栏与236高局内卡分别设计密度，长名省略，未知值/错误提示不撑坏五人名单。只展开用户选择的卡片，主列表滚动和快捷键只读行为沿用现有交互。

## 4. 数据与性能方案

### 一次读取，多队列汇总

继续使用当前大区SGP SUMMARY与LCU基础资料。每页历史只读取一次，解析后同时按queueId、英雄、时间窗口更新各模式报告；切换统计模式只是读取内存报告，不新建分页任务。OP.GG继续只提供公共攻略。

原始分页大小20只是传输单位，**不是“筛出本模式20场才能展示”的门槛**。即使首批只有1场海克斯，也立即显示该样本及范围。未出现的模式明确为暂未读到记录，不换成其他模式的数据。

### 首屏与调度

1. 已核验同账号/大区/玩家的可用内存缓存先显示，并保留实际截止时间。
2. 调度改成单页任务：每名待准备玩家先获得一次首批尝试，再安排任何玩家的第二页。慢玩家的一次重试排入后续轮次，不占满整轮首屏机会。
3. 后续页在玩家之间轮转；同一玩家只允许一页在途。维持两路SGP并发、现有总期限与页数上限，失败退避仍生效。
4. 熟练度、赛季元数据不能成为首批历史显示的前置屏障；迟到时只补对应字段。排位在赛季未确认时可显示已明确标注的近期指标，不能先称本季。
5. 分页增量聚合，按现有节流发布，首份结果和终态及时通知；新模式分类不产生逐场详情请求。
6. 非排位默认到30天覆盖即可停止；已完成的12小时/30天指标独立可用。排位赛季补齐在所有玩家首批之后继续，不阻塞已具备数据的卡片。
7. 玩家离开、换号、真实新局等沿现有取消和迟到隔离机制；同一局选人→加载→局内复用已有进度，不重新从第一页扫描。模式切换、开合卡片和主题切换不增加统计读取次数。

现有180秒、500页仅作为硬上限，不是正常展示等待时间，不因支持更多模式扩大。阶段预算的变更另行评审；本方案优先降低展示等待与重复工作。

### 报告、缓存与兼容

- 模式目录由Go输出展示所需能力，前端不再用“不是440就是420”的判断。
- 报告按精确队列保存本季（适用时）、12小时、30天和英雄指标；每个窗口携带状态、截止时间、覆盖边界、有效样本和缺失原因。整体页数不能冒充当前模式场次。
- 以一次解析的记录增量更新模式/英雄汇总；旧记录按比赛编号去重，防止阶段恢复重复累计。过期窗口重新计算时仍使用已核验缓存，不能重复计数。
- 报告合并改为逐模式、逐窗口比较覆盖和时效。当前“总read更多优先”的整份替换策略可能丢掉新模式的有效结果，必须一起调整。
- 模式筛选与排位参考分别建模，过渡兼容现有420/440消费者；Wails绑定通过固定生成入口更新。主页独立战绩筛选不与对局统计选择互相覆盖。
- 冻结复盘携带统计模型版本及当局模式，旧缓存缺新模式字段时解释为未知，不能生成0场。统计仍保持本机内存，不新增玩家统计落盘或新服务端。

## 6. 可验证的验收标准

- 混合420/440/450/2400及其他队列的固定输入，逐项核对场次、胜负、KDA、英雄和窗口边界，包含重开、跨赛季、未知字段、重复记录。
- 调度测试阻塞某玩家后续页，证明其他玩家首批仍能取得；全部待处理首批尝试先于第二页。验证重试公平性、最多两路请求和全局预算不超限。
- 相同输入及时间范围，新增模式汇总不增加历史页请求；选择模式、换英雄、开合窗口各执行多次，历史请求增量为0。换英雄只允许攻略按既有规则更新。
- 合成网络固定每页1秒、五名无缓存玩家且无需限流退避时，五人首批目标在4秒内全部发布；测量自首个历史请求开始，并另行报告完整连接→首屏耗时，不能将此数字称为国服网络保证。
- 缓存模式切换目标为P95小于200ms，记录实际Windows测试主机与样本；最终以实测为准。首屏和30天覆盖耗时分别统计，避免用空壳页面显示代替有效数据速度。
- 模式2400→450→420、新局、换账号、断线恢复时不串数据；归档筛选不改变本局攻略或统计。
- 海克斯卡不显示峡谷位置；单双排段位明确标为排位参考；已有报告无海克斯记录时不借普通大乱斗填数。
- 自动验证通过后进行Windows国服验收；用户已确认的18项PASS保留历史结论，受本次修改影响的模式/数据/窗口项目做针对性回归。

## 7. 能实现与仍待来源核验

可基于现有数据链实现：常规胜负模式的分队列统计、当前英雄表现、模式自动跟随、排位参考分离、窗口同步及公平分页。这些不依赖OP.GG提供国服玩家数据。

仍不能由本次方案承诺：来源未返回的完整生涯统计、任意网络下固定秒数读全30天、玩家每局具体强化选择、游戏当前三个强化候选自动识别，以及尚未验证的竞技场名次语义。英雄公共强化推荐与玩家实际选过的强化分开处理；本功能不顺带改变组队识别覆盖范围。

## 9. M4实施与字段依据（2026-11-13）

本批通过已有LCU嵌套stats和SGP扁平summary解析`subteamPlacement`，`playerSubteamId`只用于解析时校验，不导出或落盘。1700与1710共用竞技场能力但分别聚合，地图明确冲突时拒绝统计，不将普通`win`解释成夺冠或普通胜负，也不将短时竞技场误判为重开。

可复查公共契约：

- [LCU OpenAPI](https://github.com/KebsCS/lcu-and-riotclient-api/blob/main/lcu/swagger.json)：`LolMatchHistoryMatchHistoryParticipantStatistics`和`LolReplaysGAMHSParticipantStatistics`均定义上述两个整数统计字段（读取日期2026-11-13）。
