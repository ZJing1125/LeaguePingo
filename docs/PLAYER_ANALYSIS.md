## 2026-11-21 单场复盘与玩家资料修复方案（待实施）

基于 `dev@0dedb38` 核对。以下为本轮设计及验收条件。下文 BUG-0059/0062 所记的二次点击是旧交互，实施第一批时同步更新项目规则与浏览器断言。

### 第一批 · 打开出装符文就能复盘

**现有原因。** `MatchDetails.vue` 自动读记分板，出装和时间线标签各有一个读时间线按钮，共用一个忙状态。即使按钮消失，`MatchBuild.vue` 也只能展示匹配当前参与者编号的有效购买和升级事件。LCU 请求成功后，`internal/source/match_analysis.go` 直接返回解析结果。有帧但缺目标事件也可能成功，现有路径只在本机请求出错时尝试大区时间线。截图无法单独确定是来源缺事件、解析丢失还是目标匹配问题。

**玩家看到的顺序。** 首次进入「出装符文」或「时间线」即表示要查看这场的过程。先画出已知的终局装备和符文，原位加载购买顺序与 Q/W/E/R。两页共享同一个在途请求和结果。详情尚在读取时记住当前标签，详情就绪后接续；离开两个过程标签前尚未发出的读取撤销。列表、概览和团队分析产生零次时间线读取。复用当前连接、玩家、对局的 5 分钟缓存，关闭、断线或切局取消无主请求并丢弃迟到结果。冻结复盘只使用已有数据。

**补齐过程。** 用同场同人的源数据核对全场事件数、目标购买/加点数、过滤后可展示数及被过滤原因，只记录类别和计数。先修复经样例证实的字段或编号映射。在有效长局中，如果本机帧有效但目标事件类别覆盖不足，复用已有的可信当前大区 DETAILS 路径，在原单场预算内最多补查一次。大区、比赛或人员校验失败即停止。按购买交易、技能加点两类分别选用可核验的完整序列，保持真实时间与撤销语义，避免重复叠加事件。部分失败保留另一类及符文；超时允许原位重试，来源确实缺记录时显示一行「购买顺序未提供」或「加点顺序未提供」。短局没有购买或加点也是合法结果。

**碎片单独处理。** 碎片取自对局摘要的 LCU `stats.statPerk0/1/2` 或 SGP `perks.statPerks.offense/flex/defense`。当前视图整体优先选用详情里的个人摘要，可能遮掉同场战绩摘要已有的碎片；`positiveIDs` 也会压掉空槽。先复用同连接、同场、同一已核验玩家的字段，分别保留三个槽位、重复 ID 和缺失值，旧缓存的短数组不能用来猜槽位。如果两份已读摘要都缺失，且存在尚未读取的可信 SUMMARY，可在本标签的同一次预算中至多核对一次；优先使用进程内已有数据。保持主副系立即可读。三个槽位全缺时折成一行，释放空白区域。

**验收。** 浏览器从零缓存直接点「出装符文」，验证目标玩家开场和回城购买、撤销记录及加点次序；切时间线再返回，前端逻辑读取共一次。覆盖红方目标、局内身份编号不同于数组下标、仅有金币帧、同场摘要有碎片而详情缺失、只缺中槽、重复碎片、重开、断线和快速切局。Go 夹具分别断言 LCU 完整时零补查、部分时各补查上限、来源冲突拒收。国服以一场能对照回放的正常灵活排位核验，再用一场重开检查空数据结果。

### 第二批 · 恢复玩家资料，按队列解释段位

**现有原因。** 图四两个段位及 LP 已出现，缺的是胜负和胜率；图五已有战绩，但头像、等级、隐私和两种排位的资料都缺；图六仅灵活排位未得到确认。`internal/source/ranked.go` 返回一个队列即可置整体 `ready`。头像、等级齐全时，前端可能跳过资料补齐，Go 也可能把这份资料作为五分钟内的新鲜结果。刷新若只返回一个队列，`mergeProfile` 可能覆盖之前另一队列的结果。另有一条可单独复现的路径：同一响应的两个容器即使段位相同，胜负计数冲突也会让整个队列被剔除。切回已有玩家页签在 `App.vue` 只更新活动键。截图不能证明某个玩家未定级或设置了隐私。

**取数与恢复。** 保留战绩先显示的流程。搜索、点击名单和重新激活玩家页签统一检查可见玩家的头像、等级、隐私状态及 420/440 两个队列。复用现有 `EnsureProfile`、排位读取及调度，一份排位响应可填充两个队列。按缺项取数，头像资源失败不阻塞段位。仅当前身份、当前连接可回填。离页可取消；切回后对未完成项恢复一次，合并在途请求，遵守现有超时与失败冷却。两个队列分别保存状态、获取时间及同赛季已核验值，部分刷新保留另一队列及其原时间。明确的新赛季或未定级结果终止旧值沿用。对于同源同赛季的重复记录，保留一致的段位，隐藏冲突的计数及其胜率；段位本身冲突时保留待核验状态。胜负分子和分母必须同源同口径。

| 当前队列的证据 | 玩家看到的内容 |
| --- | --- |
| 有段位、LP，胜负都可信 | 段位、LP、胜负和胜率。真实的 0 LP 正常显示 |
| 有段位，但只确认胜场 | 段位、LP 和已知胜场。已有可信的同队列赛季样本可独立显示「本季已读」胜负；分母未知时隐藏胜率 |

| 正在读取、队列缺项、读取失败 | 分别显示短暂加载态、「该队列段位未取得」、失败时的重试。仅有明确受限信号时才说明受限 |

**验收。** 以「两队列有段位、非本人负场受限」「有战绩但基础资料首次失败」「单双排有段位、灵活明确未定级」「只返回单双排，灵活状态未知」四类夹具覆盖搜索与名单跳转。另测 A→B→A、超时后恢复、只刷新一个队列、换号和换赛季。核对已知字段不消失、旧玩家结果不串入、20 场列表数据不用于推断段位或整个赛季胜率。国服对齐玩家、大区、队列、赛季逐项核验。

### 第三批 · 团队分析只保留一份十人明细

页面要回答「双方差在哪，这个指标上谁贡献最多」。当前 `TeamAnalysis.vue` 同时为六个指标各画一份十人名单，五对五时共 60 个玩家条目；名字主要依赖悬停。采用一张紧凑的双方总量表和一份选中指标的明细，复用 Vue、现有头像、战绩跳转、主题和 `teamMetric`。

- 上半区固定蓝、红两列展示击杀、金币、英雄伤害、承伤、视野得分和补刀。指标名同时是选择控件。首次默认英雄伤害；一个指标缺字段时仍能查看已知个人数值。总量继续要求完整阵容及相应字段齐全。
- 下半区仅显示当前指标的两队贡献。队内按数值降序，同值稳定排序，未知排末；两侧共用刻度、实数右对齐。显示英雄头像及可见玩家名，两者沿用已有可跳转身份规则。查看对象仅在其行标识一次。颜色只辅助区分，蓝方、红方用文字标明。
- 1280×800 的目标是在截图同等大小的弹窗中看到双方总量和两队各五行贡献。窄窗改为上下分队，可纵向滚动。切指标仅用内存数据，支持键盘操作和深浅主题，竞技场沿用小队视图。

**验收。** 用图三的读数作阅读任务：能直接读出击杀 58 比 36、金币 74,713 比 65,292；切换到视野能找出双方最高者和查看玩家。核验每个总量与现有记分板口径一致，缺失显示「—」、真实零显示 0、局部数据不绘制虚假总量或比例。浏览器断言只有一份玩家明细，切指标零来源请求；在 1280×800、1100×760 和 880×620 下检查可读性、键盘焦点与头像/姓名跳转。

**交付顺序。** 先做出装与资料两条数据链的回归，再调整团队布局。每批分别记录实现、合成回归和实机结果。真机核验集中在最后，可复用现有玩家数据审计的脱敏统计。当前没有截图对应对局的源响应或同赛季段位核验，以上为实施及验收设计。

## 数据与交互约束

- 概览回答“这名玩家最近表现与擅长什么”，战绩列表回答“这几场怎么打”，详情回答“这一局为什么值得复盘”。标题与最大数值对应各自问题。
- 首页只代表已核验当前账号；查询别人不替换首页。主窗口与赛前/局内辅助数据保持隔离。
- 排位聚合、近期筛选样本、7天已读记录、全部模式熟练度是四种范围，标签不能混用。筛选、翻页和切详情标签不重置原独立ScoutReport。
- 保留原模式/10–50场/继续查找/停止/分页/跳页/失败保留/离线缓存和首页单场原位查看。身份未知、字段缺失和真实零分别处理。
- 点开某场详情即是对该场MatchDetail的明确请求：自动一次、使用原串行调度与12秒预算并有界缓存；列表不预取，也不逐场扫描。时间线仍只在用户明确点击时读取。渲染、切标签、切主题和换页不产生额外详情请求；换号/连接变化拒绝迟到结果。
- 跨多个赛季的完整段位轨迹、历史LP变化、OP评分、对线评分与AI标签目前没有已核验来源；仅呈现响应中可验证的最高/上一季记录，不能用当前段位冒充历史。
